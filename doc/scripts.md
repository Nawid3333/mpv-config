# The scripts

The design of each script in `portable_config/Scripts/` and `portable_config/script-modules/`, and the
reasons behind it. What each script is for, the FastStream contract and the validation checklist are in
AGENTS.md; this file does not repeat them.

## speed-presets.lua

- A preset key sets its speed; the same key again goes back to the speed that was active before that key took effect. The memory is per key and per session: q (3x) -> y (5x) -> y gives 3x, where one shared "previous speed" would send that last y back to whatever came before q.
- The value arrives as the binding's `arg` (`script-binding speed_presets/preset <value>` in input.conf), so the handler is an `mp.add_key_binding` one (validation checklist item 2) and `complex`.
- r is the 1x preset. s/d, `[ ] { }` and the uosc slider are adjustments, not presets: they move no key's memory, they only become what the next preset press goes back to.
- The banner is top left, away from the video and shader banners on the right; its id `speed` is shared with speed-button.lua, so one banner shows the latest speed.

## speed-button.lua

- The badge shows the current speed; a left-click steps to the next speed of the menu list (0.5x to 16x), right-click opens that list.
- Preset entries of the menu go through speed-presets.lua, so picking the active preset goes back to the speed before it, as its key does.
- `show-speed` (input.conf, after a no-osd change such as s/d or the menu's extra speeds) shows the same top-left banner, so every speed change looks alike.
- uosc draws a badge inside its button's fixed box: more than 4 characters spill onto the next button (gpu-toggles' badges have the same limit).

## remember-speed.lua

- `speed` is a global option: it carries across files within one process but starts at 1x in a fresh one. Watch-later is no substitute: it is per file (the speed of that file, not the last speed picked) and writes only on quit-with-save. So every change is saved to `~~state/speed.json` (whole or not at all, state-file.lua) and restored at the first video of a process; a missing or damaged file means nothing saved.
- Video only: songs neither save nor restore it, so a speed picked for an album never replaces the one for videos. A file counts as video only with a video track that is neither album art nor a single image (uosc's classification). track-list is empty while a file loads and between two files, so the kind is known from file-loaded on, and the restore happens there, not at script load.
- Within one process a switch between a video and a song sets that kind's speed (a song after a 3x episode would otherwise play at 3x); two files of the same kind keep whatever speed is set.
- A speed picked while a file loads (FastStream streams take seconds) is the user's choice for that file and wins over the restore and the kind switch. A speed the file brings along (watch-later's, a per-file option) is no pick: mpv applies it before the on_load hooks, where the snapshot is taken (priority 5, before every other on_load hook).
- A file's speed at unload is its kind's: the observer may hear of a change only after the next file has replaced this one.

## percent-seek.lua

- mpv's own `seek <p> absolute-percent+keyframes` never looks in the buffer on a source whose timestamps may reset (HLS and MPEG-TS, most FastStream streams): it asks the demuxer for a fraction of the file, and mpv's demuxer cache answers only time seeks. A jump into video already buffered then reads it all again and keeps the old copy beside the new one.
- So a target inside a range the buffer holds is sent as the time mpv itself makes of a percent seek on other sources (percent x duration), which the cache serves. Any other target stays mpv's percent seek: nothing to keep there, and on a TS file whose timestamps jump the byte seek is the one that lands. Both are instant keyframe seeks without OSD.
- mpv seeks into the ranges at the stream's start and end from anywhere before their first or after their last keyframe, so those count as buffered too.
- input.conf: `N script-message-to percent_seek jump <N x 10>`. State: `user-data/percent-seek` = {jumps, percent, time (nil without a duration), buffered, ok}.

## skip-forward.lua

- A file's end is what FastStream's autoplay waits for (keep-open stops there, paused, eof-reached), so a skip to the end has to arrive there. mpv's own `seek <n>` past the end of an HLS stream whose end is not buffered yet asks the demuxer, and FFmpeg's HLS demuxer refuses a time after the playlist's duration ("[lavf] Seek failed"): mpv then goes on from the end of what was buffered, and no end comes.
- An exact seek to the duration itself is a time inside the file: it decodes from the last keyframe to the last frame and lands within 0.2 s of the end. Playback then goes on, because a paused player may show the last frame without marking the end, which comes only when playback asks for the frame after it; keep-open pauses at the end again.
- A skip that would land in the last second (`END_MARGIN`) goes to the end too: a keyframe seek there can stop seconds short of it. Every other skip stays mpv's instant keyframe seek.
- input.conf: `x script-message-to skip_forward skip 60` (and 10, 5). State: `user-data/skip-forward` = {skips, seconds, to_end, ok}.

## pause-flash.lua

- uosc shows its UI only when the mouse moves, so a pause made with the pointer still (Space, a media key, the cursor hidden in fullscreen) changes nothing on screen but the picture. Each step into pause flashes uosc's whole UI (`flash-ui`) for uosc.conf's `flash_duration`, the time the volume and speed flashes stay up.
- Only the change from playing to paused flashes, the stop at a file's end (keep-open) included. A pause the player starts with or carries into the next file is no change. With the pointer over the window the UI already shows, and the flash does nothing.
- State: `user-data/pause-flash` = {flashes, ok (the last one reached uosc)}.

## auto-start.lua

- `pause`, `sub-delay` and `audio-delay` are global options and carry over to the next file in the same process. FastStream's next episode and mpv-single.exe both hand the next file to the running player (loadfile replace), so a paused file (keep-open pauses at the end) would leave the next one on its first frame, and one episode's delay would shift every later one.
- The pause is cleared once per file, at file-loaded; a pause during playback stays. A pause set during the load itself is cleared too: it cannot be told from an inherited one. The cache's own buffering pause (paused-for-cache) is separate and untouched.
- One file stays paused: the one a quality switch made while paused loads (faststream-quality.lua). The switch names it in `user-data/auto-start/keep-pause`, read and cleared at the next file-loaded, so a switch whose file never loaded leaves no pause for the file after it.
- The delays go back to 0 when a file unloads, not at the next file-loaded: by then mpv has applied that file's own delays (watch-later, a per-file option, `--sub-delay`), which must survive.

## gpu-toggles.lua

- Shader upscaling. Shift+A, Shift+Y and Shift+S live in input.conf and send script messages here, and the uosc `upscale` toolbar button and the Video > Upscale menu use the same messages, so state and banners live in one place. The cycle is Off -> Auto -> Anime -> Movie -> Off. It starts at Auto.
- Auto upscales FastStream streams only: their URL carries an `fs-content=anime|movie|native` fragment item (AGENTS.md, "FastStream contract"; read as the last whole item through faststream-fragment.lua, up to its first non-letter, so an empty `fs-content=` is no tag). Anime presets on anime, Movie presets on everything else, none on `native` (FastStream's @native tag: the user wants no upscaler there). A native stream, a local file or any other source gets no shaders unless Anime or Movie is picked: the button reads "Off" there, the menu hides Auto and the cycle skips it (Off -> Anime -> Movie -> Off). The mode itself stays Auto, so a FastStream stream loaded next still gets its preset. Every file load re-applies the mode; a named choice (Anime/Movie) stays across files.
- Anime: Anime4K C+A, chosen by eye over ArtCNN and CuNNy-4x32-DS; do not swap in a "faithful" 2x CNN. Its own AutoDownscalePre stages adapt it to the real target ratio. Quality Fast uses Anime4K's own low-end template of the same Mode C+A (M instead of VL for the first upscale, S instead of M after it): the same look for about half the work. Anime lines: `crisp` runs Anime4K's Restore step (crisper, thinner lines, right for lines a source blurred), `drawn` leaves it out (Mode C), one setting for all anime.
- Movie: the chain is picked by the real scale to the display. Below 2x a 2x CNN followed by a downscale loses 1-2 dB against plain scaling (it overshoots, then the downscale throws the gain away), while SSimSuperRes, which targets the output size directly, is best or tied on every metric; from 2x (`MOVIE_FSRCNNX_MIN_SCALE`) FSRCNNX's fixed 2x lines up with the target and FSRCNNX + SSimSuperRes wins (+2 dB at 2x). ArtCNN never wins on clean material. The downscale after a 2x CNN matters: mpv's default `hermite` is soft, so the Movie presets set `dscale=ewa_lanczossharp` while active, and everything else gets the startup `dscale` back.
- Not used: FSR (EASU/RCAS) measures worse than plain ewa_lanczossharp and cannot stack with FSRCNNX (once FSRCNNX has upscaled, FSR's `WHEN OUTPUT > input` gate is false). No vf-based upscalers (AI restoration through VapourSynth/ONNX): a frame-by-frame network has no temporal consistency (texture can shimmer), needs the GPU in bursts beside the renderer, and cannot follow the 2x-16x speed keys. Everything here is spatial GLSL inside the render pipeline.
- Sharpening: the chains are chosen for fidelity, and what reads as sharper is edge contrast at the shown size, which fidelity metrics penalize. Both Movie chains end with adaptive-sharpen on the OUTPUT hook, at display resolution after all scaling: edge-adaptive, with anti-ringing limits, leaving flat low-contrast areas (where compression noise lives) alone. Its strength is the `curve_height` PARAM, set through `glsl-shader-opts`, so a level change needs no recompile; Off <-> on swaps the shader list. It is left out when the video is not enlarged (sharpening a downscale only adds aliasing); an unknown scale counts as enlarged. Auto strength is display scale - 1, clamped to 0.5..1.5: across 1.33x-3x it tracks the clean master's own edge sharpness, which no fixed level does. Other sharpeners do not qualify: FSR RCAS, CAS and NVSharpen run only without scaling or as the scaler itself, mpv's `--sharpen` is vo=gpu only, and nlmeans_sharpen_denoise before the chain smeared detail on x264 encodes.
- Chroma: nearly every movie file is 4:2:0, so its colour planes are enlarged twice the luma ratio (a 720p source on a 1440p display: 4x), which gives soft, bleeding colour edges no luma shader touches. Both Movie chains start with CfL_Prediction (chroma from luma, pinned in install-shaders.ps1): it predicts colour from full-resolution luma by local linear regression, blended with a normal resampler where the two do not correlate. It hooks CHROMA and binds LUMA, so it follows FSRCNNX's 2x output when that runs. Cheap, and no effect on 4:4:4 or RGB.
- Quality: `auto`, `high` (the full chains) or `fast`. A chain fine on a fast GPU can be many times too slow on a weak one, so Auto does not guess from the GPU's name: the first time a high chain runs for a screen and source size, the render passes' GPU timers (`vo-passes`) are read after `MEASURE_AFTER` seconds of play (not while paused, buffering or while the shader warm-up draws). Over `BUDGET_SHARE` of a frame's time (half a frame) Auto takes the fast chain for that size from then on, with a banner; when the fast one is too slow too, upscaling is off there. Every chain stays selectable, and the menus list High and Fast with what each cost here. `forget-measurements` starts over (a new GPU or driver); `set-cost` records one by hand (the tests: `--vo=null` has no GPU timers).
- The screen: `auto` (the monitor mpv is on) or `WxH`, the size the Movie chain, Auto sharpness and the measurements are chosen for; Anime4K's stages follow the real output size anyway. The display and source size are read at most once per action and only when it needs them (`display-width/height` wait for the video thread); `width`/`height` are before rotation, so a portrait video shown upright counts as a downscale. The source's size class is its pixel count as a 16:9 height (1920x800 is 1080p-class).
- A preset whose shader files are all missing clears the list instead of leaving the previous chain running unseen, and reports the failure; single missing files are dropped, as mpv aborts the whole list when one fails to load. The list is replaced in one `change-list ... set`; the sharpening strength is set first, so the sharpener never runs a frame at a stale value. An unchanged chain is not reloaded, but a user's change still gets its banner.
- The button is managed (`button:upscale`, pushed with `set-button` like speed-button.lua's), and an unchanged button is not sent again, as uosc repaints on every push. Its badge stays at 4 characters: uosc draws it inside the button's fixed icon box, and a longer one overlaps the next button. The first push repeats every half second (at most 10 s) until uosc has it.
- `script-binding gpu_toggles/<name>` finds only bindings added with `add_key_binding`, not script messages, so both exist; the keys themselves are in input.conf. Every action goes through `entry()`, which reads the display fresh and counts finished actions in `user-data/gpu-toggles/applied`: the shader warm-up waits on that counter, so the initial button push and settings.lua's `publish-quality` request do not go through it.
- Options: `script-opts/gpu_toggles.conf` (`movie_sharpness`, `quality`, `remember`). The menus' choices are remembered per PC in `~~state/movie-sharpness.json` and `~~state/upscale.json` (quality, screen, anime lines, measured costs keyed like `anime-high|2560x1440|1080p`) and win over the conf; only a chosen quality is saved, so a later conf change still counts. The shader warm-ups run with `remember=no` and neither read nor write them.
- State: `user-data/gpu-toggles/` `preset` (the family on screen, which the tests read), `quality` (the settings, Auto's pick, the measurements and the menu items that settings.lua embeds) and `applied`.

## shader-cache/

### main.lua

- Keeps mpv's shader cache warm. At every start fingerprint.lua compares the stamp in the cache folder with the current libplacebo version, display driver version (reg.exe, about 25 ms, no console window: mpv spawns with CREATE_NO_WINDOW), shader files and cache file count, off the playback path; nothing waits for it.
- Stale: `start_delay` seconds after the video starts playing (so its own start is not slowed), host.ps1 runs warmup.lua in a second mpv embedded in a window that is never shown (host.ps1 says why each simpler way fails), at below-normal priority, its clips paused except for a few stepped and played frames per chain, so the GPU stays nearly idle. mpv opened with nothing to play has no start to keep clear: it warms after `idle_delay` seconds of idle. The chain the video uses compiles itself on its first frame; the warm-up covers every other chain and scale tier, so a later switch or the next video does not hitch. Nothing blocks: the video starts normally, with a small progress bar top right (a notify.lua banner, so messages stack). A quick check that compiles nothing shows no bar.
- Quitting mpv ends the warm-up with it (mpv ends its subprocesses on exit, and the warm-up quits when host.ps1's window goes); it runs again at the next start.
- A failed or timed-out warm-up is not retried for the same fingerprint (`shader-warmup.failed`), not even for a new screen, and is said once on screen; `installer\warm-shader-cache.ps1` and "Rebuild shaders" still run it. warmup.lua's exit 6 (steps never drawn: a minimized window, a locked screen) is the moment's, not the cache's, and is retried like an interruption. A warm-up ended from outside (`taskkill /F` gives exit 1, as FastStream's e2e tests do to every mpv that starts during a spec, or a crash) is retried at the next start, but a third time in a row for one fingerprint counts as a failure, so a warm-up that crashes every time cannot loop.
- The screen the cache was warmed on decides which branches of the chains the clips reach, and warmup.lua adds clip sizes for the branches the standard ones miss there. It is known only once the window is up, so it is compared at the first playback start; a stamp without a screen never differs.
- The warm-up process gets notify.lua (gpu-toggles announces each switch as a banner), settings.lua (the HDR brightness, read-only), `--untimed` (a stepped frame shows at once) and `gpu_toggles-remember=no` (it steps through the Movie sharpness levels, which are not the user's choice).
- "Rebuild shaders" (Video > Upscale, and the upscale button's menu) deletes mpv's own compiled shaders (the `shader_<16 hex>` files in its cache folder) and warms everything again at once, whatever the stamp says. AMD's driver cache (`%LOCALAPPDATA%\AMD\VkCache`) is never touched; the driver keeps its own copies there as for every Vulkan program.
- State: `user-data/shader-cache`.

### fingerprint.lua

- Shared by main.lua (the startup check in every player) and warmup.lua; loaded with `dofile()`, not `require()`, because warmup.lua runs as a plain `--script`, outside this folder's module path.
- What makes cached shaders stale: mpv's cache (`portable_config/cache`, `shader_<16 hex>` files) holds SPIR-V compiled from libplacebo's GLSL, keyed by that GLSL, and the GPU driver's finished binaries (Vulkan pipeline cache blobs, stamped with the driver's pipelineCacheUUID). So: a new libplacebo means new GLSL and new SPIR-V; a new display driver rejects every binary blob; the cache folder may be deleted or thinned out; the shaders and gpu-toggles.lua are what the chains are made of; mpv itself could change a pass through its render settings (a quick check, escalating if anything compiles; a rebuild with only a new FFmpeg keeps the version string and triggers nothing). Nothing else starts a warm-up: not a restart, a new video, a reboot or resetting AMD's own shader cache, a second layer mpv does not control.
- The stamp and control files live in the cache folder itself, so clearing the cache clears the stamp too. mpv's own cleanup only deletes `shader_<16 hex>` and `icc_<16 hex>` (vo_gpu_next.c `cache_uninit`), so these names are safe there.
- The config signature is name + size + mtime, not content: git only rewrites a file when its content changes, and names (not full paths) keep a copied config (the test harness) matching the original. mpv.conf is in it: its render options change the passes of every chain.
- `WARMUP_VERSION` is bumped when warmup.lua's clip matrix or way of drawing changes, or shipped-cases.lua's list (AGENTS.md); removing runs needs no bump, a warm cache stays warm.

### warmup.lua

- Runs in its own mpv process, never inside the player, always embedded in a window that is never shown (host.ps1): main.lua starts it when the cache is stale, `installer/warm-shader-cache.ps1` on request (and with `check=yes` for the gpu test tier). Nothing of it is on screen and it gets no input. mpv loads only a folder's main.lua, so this file is never a player script by accident.
- It draws every upscale chain once in the real renderer, so libplacebo's compiled shaders are in the on-disk cache before a real video needs them; a cache miss costs up to about 0.3 s before the first frame.
- A cache entry is keyed by the passes that run, not the video size, so the matrix covers each scale tier the chains branch on (Anime4K's x2/x4 AutoDownscalePre, Movie's FSRCNNX at 2x and up, no sharpening when not enlarged), 8-bit and 10-bit sources, through d3d11va-copy, the one hardware decode path (Vulkan decoding is never used, AGENTS.md).
- The standard clip sizes reach every scale branch on a 1440p screen (Anime4K's WHEN lines: no upscale up to 1.2x, x2 + downscale up to 2x, x2 alone up to 2.4x, x2 + downscale + x2 up to 4x, then x2 twice; Movie's SSimSuperRes + sharpening below 2x, FSRCNNX from 2x). Another screen misses some (4K has nothing between 1.2x and 2x, 1080p nothing at 4x or more), so a clip at the middle of each missed branch is added, in both formats. A quick check that compiled nothing draws no screen sizes and keeps the screen they were last drawn for in its stamp.
- The quick check (only shaders or presets changed) stops after its first clips if they compile nothing: 720p and 1080p (Movie's two chains), 10-bit, and 480p, the one size at which Anime4K's AutoDownscalePre_x4 runs on a 1440p screen. A quick check makes only its own clips (each costs seconds of encoding); one that turns into a full warm-up makes the rest then.
- Shipped cases (shipped-cases.lua): after the matrix a full warm-up also draws what real playback needs beyond it, each from a 1 s clip in exactly that format and colour tagging (mpv's own encoder, cases.lua), decoded the way the case says, through its chain, at its displayed scale (video-zoom against this window's fit). A case whose clip cannot be made is skipped with a RESULT INFO line, never fatal.
- Each clip sits paused and every step frame-steps just far enough to prove the new chain was drawn (`settle()`): a switch counts as drawn once gpu-toggles has finished every action sent so far (its `entry()` counter) and SETTLE_FRAMES more frames were queued. The VO draws frames in order and reads option changes at the start of each draw, so by then the first frame with the new chain is finished; a long compile stalls the VO and with it the stepping. Then each clip plays a few frames (`play_frames`): a playing video draws some passes slightly differently from a stepped one (extra specialization constants). Looping clips run under `--untimed` and never reach an end where stepping would stall.
- The process loads only gpu-toggles.lua, uosc (its UI is drawn over every real video, so its passes belong in the cache), notify.lua, settings.lua (read-only, `settings-write=no`) and this script: nothing that keeps state runs there. Progress goes to `shader-warmup.progress` in the cache folder, for main.lua's bar and the manual script.
- Cache misses are counted from libplacebo's log ("shaderc compile status" appears once per GLSL->SPIR-V compile, never on a hit; a driver pipeline creation of 2 ms or more is a compile too). It prints `RESULT INFO <step>: <n> compiles` and, with `check=yes`, a final RESULT PASS/FAIL. A step whose frames were never drawn proves nothing and fails the run. Exit codes: 0 done, 1 check found misses (or could not draw), 2 setup error, 3 hard timeout, 4 stamp not written, 6 steps never drawn; a full warm-up that draws nothing reaches the hard stop first and exits the same way.

### shipped-cases.lua and cases.lua

- shipped-cases.lua lists what real playback needs beyond the matrix; the list was found by measuring and is kept by hand. A kind of video that still stutters on its first start after a full warm-up (a log with `--msg-level=vo/gpu-next/libplacebo=debug` shows "shaderc compile status" lines) is a new case.
- A case: `clip` (size, FFmpeg pixel format, encoder, colour tags, SAR, film grain), `hwdec`, `chain` ('off' | 'anime' | 'movie'), and optionally `unscaled` (drawn 1:1, a window at the video's own size, which is how mpv opens a local file), `deband`, `eq`, `rotate`, `overlay` (an RGBA bitmap over the video: thumbnails, picture subtitles), `subs` (a libass line), `as_size` (drawn at the scale a source of that size has in this window). A clip can be a shipped file (`clip.file`) where no encoder can make it: Dolby Vision, whose RPU reshaping is a pass of its own. Otherwise the clip is fitted to the window, and has the real size the case stands for: gpu-toggles picks Movie's passes and sharpening from the true display scale, so a smaller clip zoomed up would draw a different chain.
- cases.lua turns a case's `clip` into a lavfi source, encoder options and a name: `w`, `h`, `pix` (FFmpeg's pixel format), `codec` (mpv's encoder, `--ovc`), `matrix`/`primaries`/`gamma`/`levels` (mpv's names), `sar` ('64/45': anamorphic), `grain` (AV1 film grain, libsvtav1 only). sar and grain are added to the name only when set, so clips made before stay valid. mpv's encoder drops primaries and transfer from the frames but passes them on as encoder options.

## settings.lua

- The Settings menu (right-click menu > Settings, the gear button `button:settings` in the control bar, `script-message-to settings open`) and the Welcome menu (F1, Help, and the first start through welcome.lua; `open-welcome`): the same settings on top, then every feature with its key. The menus stay open, mark the recommended choice and keep every option selectable. Every setting explains itself in its submenu (a dimmed note on what it does, a pro or con next to each option).
- Buffering: FastStream's buffer options with its names, meanings and defaults (stream-buffer.lua does the buffering): predownload the whole video (on), its maximum size (5 GB), RAM for buffered video (Auto by this PC's memory, FastStream's 2 GB from 16 GB on), keep video on disk when that RAM is full (on), seconds ahead (300) and behind (20). Every number also takes 0 (none), no limit, and any value typed in (Custom..., through mpv's console line; the menu closes while the line is open, since an open uosc menu would take what is typed). Sizes count 1 GB = 10^9 bytes, as FastStream does.
- Start and stalls: Adaptive (the default), start at once, or buffer N seconds first and after a stall (`cache-pause-initial` / `cache-pause-wait`). A seek never waits: mpv clears its restart state on every seek (player/playloop.c, `reset_playback_state()`), so `cache-pause-initial` would hold playback after each seek until enough is read. It is on until the file's first start (`playback-restart`) and off from then on; a stall still waits `cache-pause-wait` seconds.
- Adaptive: while mpv waits (before a file plays, and in a stall) playback stands still, so the buffer grows by what the line brings. q, the seconds of the stream per second, is the largest of three readings, so the wait ends as soon as any of them says the line keeps up: how far the buffer's end moved since this wait began, how far over the last `ADAPT_SLOPE_SECS`, and mpv's `raw-input-rate` over the bytes the buffer holds per second of the stream (on HLS it runs ahead of the buffer at the start). The buffer's end is used, not `cache-duration`, which subtracts the reader the decoders move at the start. A line that keeps up (q >= `ADAPT_FAST`) waits `ADAPT_SHORT` seconds of buffer (mpv's own stall default), which avoids a stall right after the start on HLS; a slower one waits for what drains in `ADAPT_PLAY_ON` seconds, before the first frame never longer than 3 s, in a stall up to `ADAPT_STALL_MAX` (the same total wait in fewer, longer pauses). mpv compares the buffer with `cache-pause-wait` on every update, so a lower value ends a wait at once (`handle_update_cache()`). The tests stand in for the line with `adaptive-line <q>`.
- Upscaling quality, screen and Movie sharpness belong to gpu-toggles.lua (and `~~state/upscale.json`); their items come from `user-data/gpu-toggles/quality`, asked for fresh when a menu opens.
- HDR brightness: `target-peak` while an HDR (PQ/HLG) video plays, the screen's peak in nits that the tone mapping aims at. Auto is mpv's own default (203 nits on an SDR desktop; with Windows HDR on, what the display reports). SDR video always gets auto, since a peak set for every file makes SDR about 78 % as bright.
- Subtitle / audio language: mpv's `slang` / `alang`. Empty is mpv's own choice: subtitles in Windows' display language when the audio is another one (`subs-match-os-language`), the file's default audio track. Languages apply before the first file, as mpv waits for every script's main chunk before it opens one.
- The screen: what Windows reports for the window's monitor (`display-width` x `display-height` @ `display-fps`), read once the three have settled. Every screen seen is remembered with its own HDR brightness; the first takes the PC-wide value, a new one starts at Auto (a peak tuned for one panel is wrong for the next) and a banner names it, with F1 to check its settings. The refresh rate can arrive a moment after the size, so a size without one waits for it rather than being remembered as a screen of its own. The upscaling follows the screen by itself (gpu-toggles reads it per action; the shader warm-up warms again for a new size). The tests report screens with `screen-seen` (`--vo=null` has no display).
- yt-dlp's JavaScript runtime: mpv.conf has yt-dlp solve YouTube's challenges with Node.js (`js-runtimes=node`), which yt-dlp looks for on PATH. The one-click install puts none there, as the FastStream helper's node.exe is private (installer/install-faststream.ps1), so yt-dlp is pointed at that one when it is there; without it, the formats that need the challenges solved are missing.
- Stored per PC in `~~state/settings.json` (gitignored), written whole or not at all through state-file.lua; a damaged file is kept aside as `settings.json.corrupt-<time>` with a warning, and one that could not be moved aside is never saved over. A PC that ran this config before (any of its state files is there) keeps what mpv.conf gave it (German, then English, 350 nits, 1 GB as the RAM budget), so an update changes nothing there; a new install starts from the recommended values. That decision is made once per PC. The start and stall wait is Adaptive everywhere.
- `settings-write=no` only applies what settings.json says and never writes it (the shader warm-up loads the script for the HDR brightness its clips are drawn with). Other scripts read `user-data/settings/buffering`.

## stream-buffer.lua

- A stream is buffered the way FastStream does it, with FastStream's settings, names, meanings and defaults. settings.lua shows them (Settings > Buffering), keeps them in settings.json and publishes them as `user-data/settings/buffering`:
  - `download_all`: predownload the whole video (on); it stops at `max_video_size`.
  - `max_video_size`: bytes predownloaded at most (5 GB; 0 = nothing predownloaded, only `buffer_ahead`; -1 = no limit). Going to disk never more than 60 % of the temp drive's free space, as FastStream; in RAM only never more than the RAM budget.
  - `ram_budget`: bytes of the video kept in RAM (Auto by the PC's memory; 0 = none; -1 = no limit, all in RAM).
  - `buffer_to_disk`: beyond the RAM budget the video goes on disk (on); off, nothing is written and the buffer stops at the budget.
  - `buffer_ahead`: seconds read ahead when predownload is off, has stopped or ran out of space (300; 0 = nothing ahead; -1 = no limit).
  - `buffer_behind`: seconds kept behind playback while the buffer is a window (20; 0 = dropped at once; -1 = all). While the whole video is predownloaded nothing is trimmed (FastStream keeps a video that fits).
- How mpv does it: a stream starts in RAM (`demuxer-max-bytes`). Just before the RAM budget is full, `cache-on-disk` is switched on: the RAM part stays, new packets go to a temp file in `%TEMP%` and count only their metadata (about 70 MB per hour of a 24 fps video with audio) against `demuxer-max-bytes`. That limit is raised at the switch and again whenever the metadata nears it; unraised, reading stops just past the RAM part.
- The switch must come before the limit, not at it: a demuxer sitting idle at its limit reads its new options only when playback takes a packet, so not while paused. So the RAM limit sits `HEADROOM` above the budget, and the switch comes a margin below it (two ticks of the fastest growth seen, at least 32 MB); a burst can take the RAM up to `HEADROOM` past the budget.
- Predownload is `cache-secs` at mpv's own "no limit"; a window is `cache-secs` at `buffer_ahead`. `cache-secs` 0 still leaves mpv's own 1 s read-ahead (`demuxer-readahead-secs`), so that is set to 0 too.
- The temp file is unlinked as soon as it is made (mpv's default `demuxer-cache-unlink-files=immediate`): invisible while in use and gone when the video closes, even after a crash. It only grows (mpv reuses no space in it), so a window on disk after the maximum size keeps adding what it reads; below `LOW_DISK` of free space the rest of the video stays in RAM instead.
- Behind is mpv's `demuxer-max-back-bytes`, in bytes: seconds x the stream's bitrate (measured from the packets, else what the RAM buffer holds per second of video, else 1 MB/s). On disk that counts metadata, so more than the seconds stays seekable there, at no cost. In RAM only, ahead and behind share the budget (mpv limits them apart), and at least 10 s of reading ahead always stays.
- A live stream (no duration, or a growing one, for 3 s) has no end to predownload to: it gets a window. mpv reports the cached end as the duration of a source that has none, so "no duration" alone never appears; a VOD's duration stands still from its start.
- With `buffer_ahead` at no limit the maximum size stops nothing: FastStream's rule ("the whole video is downloaded ahead, even with predownload off").
- Not in mpv (FastStream has them): a download speed limit and the number of downloads at the same time. A local file is read from its own disk: it gets mpv's default 150 MB ahead / 50 MB behind, both within the RAM budget, and never a disk copy of itself.
- State: `user-data/stream-buffer` (storage 'ram' | 'disk' | 'none' | 'local', mode 'predownload' | 'window', and why a window: 'off' | 'size' | 'live' | 'disk full').

## stream-resume.lua

- mpv's own watch-later keys a file by its path, and a FastStream path is the CDN stream URL, which on streaming sites carries an expiring token: the same episode arrives under a new URL every time. Instead the FastStream helper appends `fs-id=<16 hex>` to the URL fragment (never sent to the CDN): a SHA-256 prefix of the browser tab's page URL, the episode page, which is stable. Only files with that tag are touched; local files keep starting at 0:00.
- The position is saved every `SAVE_INTERVAL` seconds and when the file unloads, so a crash or an accidental close loses at most a few seconds. Each save re-reads the file first, so two mpv windows do not erase each other's entries.
- On reopen it resumes without asking, set at on_load as the start position (mpv fetches from the saved point directly instead of loading 0:00 and seeking), and a notify.lua banner (top right, `NOTE_SECONDS`, after the resume seek has landed) says where and that Home starts over.
- An entry is dropped when the video is finished (inside the last 8 %, at least 30 s and at most 3 min: an episode's end credits and preview), below `MIN_POSITION` (so "Home, then close" forgets it instead of resuming at 0:03), or when it has not been watched for `EXPIRY_SECONDS` (7 days; watching again resets them). Expired entries are also dropped at startup, since the next save may not come for a while.
- A start position given with the file (FastStream's player button hands over where the browser's player was, as the per-file option `start`) wins over the saved one; the position is still saved.
- The saved duration must match the reopened stream's (within `DURATION_TOLERANCE`), so a site that serves several episodes under one page URL cannot resume episode 3 at episode 2's position. A stream without a duration (live) is not saved.
- Progress is mpv's own; FastStream's browser player keeps its own. A stream from a private window (`fs-private=1`) is neither resumed nor saved; its fs-id stays for faststream-episodes.lua.
- State: `~~state/stream-resume.json`, gitignored, safe to delete, written whole or not at all (state-file.lua). Saves go through a temp file and a rename, so an unreadable file is damaged: it is kept beside as `.corrupt-<time>` and saving goes on (skipped every time, resuming would stop for good). What was moved is read again, since another window may have saved a good file over it meanwhile.

## faststream-episodes.lua

- uosc's own prev/next are playlist buttons, and a FastStream stream is a playlist of one; mpv offers no autoplay switch. So the script puts previous, next and an autoplay switch into uosc's control bar while FastStream plays a series in this window.
- The helper's properties and messages are AGENTS.md's "FastStream contract". `connected` missing counts as false. A helper killed hard (Task Manager, a Firefox crash) clears nothing: once `heartbeat` has stood still for `heartbeat_stale` (90 s, three beats missed) it counts as gone and the buttons go; a helper that never writes one is followed by `connected` alone. The helper sets booleans over JSON IPC; a `set` from a command string stores text, so "yes" and "true" count too.
- `faststream-autoplay` (also Ctrl+a) flips the setting, stores it, sets `user-data/faststream/autoplay` and says so in a banner; switched off during the 5 s countdown at an episode's end, it cancels the countdown.
- The three buttons are managed uosc buttons (uosc.conf `controls=`, their look pushed with `set-button`, as gpu-toggles.lua, source-info.lua and settings.lua do), shown only while FastStream follows this window and the file is a stream it sent. Each push carries `hide`, and uosc.conf gives the buttons and the gap after them the disposition `<user-data/faststream-episodes/shown>`, which the script sets true only once uosc has all three: uosc draws an uninitialised managed button as a question mark. A button is pushed only when its look changed, as uosc's `set-button` repaints the whole UI each time.
- mpv tells no observer when a user-data key is deleted (AGENTS.md); neither does it report a true set again while the observer still holds true. A look once a second catches both, sends a button uosc did not get yet, and notices a heartbeat that stopped.
- The keys (n, N, Ctrl+a) and the Playlist menu send the same messages in any window. With a helper following, the helper acts and speaks; without one (a file opened in mpv itself, FastStream not in MPV mode, a helper that stopped beating) next/previous step through the playlist (for a local file the next file of its folder, which autoload.lua queues), and for a FastStream video, whose episodes only its helper can open, a banner says so.
- State: `user-data/faststream-episodes/buttons` holds what was last pushed for each button.

## faststream-quality.lua

- The one Quality button and menu: the qualities this video comes in, as a managed uosc button (its badge: the one playing) and a menu that switches between them without losing the position. The qualities come from one of two places; the page's list wins when a file has both (its entries may be HLS masters).
- The page's own list. Some sites offer a video as several files, one per quality, and their player loads one. FastStream sends mpv the one its quality setting asks for, and the list as the fragment item `fs-quality=<percent-encoded JSON>` (helper 12+): an array of two to twelve `{"label": "720p", "height": 720, "url": "https://host/720.mp4"}` (height 0 when the page did not say). A tag that keeps fewer than two usable entries is no list. The file playing is the entry whose url equals `path` up to its first `#` (the helper writes the entries without a fragment); none matching leaves the menu without an active row and the button without a badge. Labels come from web pages, so they are cut by whole UTF-8 characters (uosc draws half a character as invalid text).
- A page-list switch is loadfile replace with the entry's url plus the current fragment, unchanged: the FastStream tags, `fs-quality` included, travel with the next file and the button keeps working. With it travel the position (whole seconds, rounded down), the request headers and title (faststream-fragment.lua's `reopen_options`; without them a CDN that checks Referer/Origin/User-Agent refuses the file), the helper's subtitle paths (`options/sub-files`), the user's sub/audio delay (auto-start.lua resets both at unload, and a per-file option is applied after that) and the pause state: a switch made while paused names the file it loads in `user-data/auto-start/keep-pause`, so auto-start.lua leaves that one paused.
- Only http(s) entries are loaded: the list comes from a web page, and mpv opens local files and UNC paths too. The tests set `faststream_quality-test_local=yes`, which also takes local paths: entries without a scheme and Windows paths, whose drive letter reads as a one-letter scheme.
- The stream's own qualities: an HLS master's variants, YouTube's formats (ytdl_hook's `all_formats`, on by default), a DASH manifest's. mpv makes the first two editions, one per variant (`--flatten-editions=no`, its default), and lists only the playing one's tracks; setting `edition` swaps the tracks in place. It is set file-local: `edition` itself would stay for the next file, an index into its own editions. An edition's height is read from the title mpv composes for it ("Bitrate: 2.500 Mbps (h264 1280x720 25 fps)", YouTube's "137 - 1920x1080 (1080p) (h264 ...)"); an edition that names no size is no quality, and neither are a Matroska file's editions (cuts of a film), whose tracks belong to no program. Variants mpv lists as tracks (DASH, `--flatten-editions=yes`) switch with a file-local `vid`, as a track id is the file's own and `vid` would stay for the next file with the same tracks. One row per height and frame rate (a rate above 30 is named: "1080p60"): the one playing, else the highest bitrate (HLS says it), else the first mpv lists (YouTube: yt-dlp's preferred format). The badge shows the height alone.
- An HLS variant starts over from the beginning: mpv restarts playback on an edition change for a format whose timestamps may reset (6.5 s in, back at 0), and the script seeks back. `seeking` right after the switch says that restart is pending; EDL and track switches keep their place and send none, so a later restart is never taken for theirs. A seek while the restart is pending is the user's (the switch itself sends no seek event) and wins. The seek back comes a moment after the restart, and only when no seek came meanwhile: a user seek made during the restart starts only after it.
- A pick while a file loads (a switch's own, the next episode) does nothing: the position is not known yet, and the pick would start from the beginning.
- uosc's own `stream-quality` button is not in the bar: its menu sets `ytdl-format`, which only a YouTube reload reads, and lists sizes the video may not have. uosc's Editions button hides while the editions are this menu's qualities (uosc.conf, `user-data/faststream-quality/editions`).
- The button is managed (its look pushed with `set-button`, as the episode and source buttons), gated by the disposition `<user-data/faststream-quality/shown>`, set true only after the first push reached uosc (an uninitialised managed button draws as a question mark) and false once the file offers no choice. The flags are always booleans: mpv tells no observer when a user-data key is deleted. A push uosc did not get (not started yet) is sent again every second until it has it. Between two files the last path stays, since hiding and showing the button would repaint uosc's whole UI twice; file-loaded reads the next path (the same path loaded again is no change of `path`), idle clears it.
- The menu is a uosc callback menu (as source-info.lua's): every event arrives as JSON at `menu-callback`, and "activate" carries the row's value (the entry's url, `edition:<id>` or `track:<id>`). uosc keeps a callback menu open over a switch and a file change; an open menu is updated with each change, and a row the file's list does not have does nothing. input.conf's Video > Quality sends `open-menu`; a file without a choice opens nothing.
- State: `user-data/faststream-quality/` `list`, `source` (page, editions, tracks), `current` (1-based), `shown`, `editions`, `button`, `last-load` (the url and options of the last file switch) and `returning` (an HLS switch's way back is still to come).

## source-info.lua

- The toolbar's source button (`button:source` in uosc.conf's `controls=`, a managed button whose look is pushed with `set-button`, as speed-button.lua and gpu-toggles.lua do): where the video comes from, and every link it can know, ready to copy or open. Nothing is guessed:
  - stream URL: the URL mpv opened. The ytdl hook rewrites `stream-open-filename` during on_load, so for a web page `path` (the command-line URL) and the opened media URL differ, and both are offered. Both sides are read in an on_load hook at priority 11, after ytdl_hook's (10; lower runs first). Only a web address counts as opened: for a YouTube link pasted into mpv, yt-dlp's formats arrive as an `edl://` list and a playlist as `memory://`, which no other player or browser can open, so the pasted link is the stream URL and "Open in mpv" runs yt-dlp on it again.
  - site page: the helper's `fs-page=` fragment item (AGENTS.md, "FastStream contract"), decoded, when it is a web page. Without it the rest of the button still works.
  - local file: the full path ("Show in directory", "Copy path").
- A copied or re-handed stream URL leaves out the helper's `fs-*` items and is not decoded: `%2B` and `%26` inside a signed token or a proxied address are part of it.
- Copying: each entry has a "Copy" sub-item, and uosc's menu copies the selected entry with Ctrl+C; the actions report whatever the selected entry's value carries. Copying goes through mpv's `clipboard/text` property, which uosc's own copy uses too (plus its ziggy helper, which only uosc's process can call), so there is no fallback: a missing property gives a failure banner, not a silent no-op.
- Opening: a stream URL opens again in this player (loadfile replace, which keeps the cache warm and the resume state), with the request headers and title it came with (faststream-fragment.lua's `reopen_options`): the helper hands them over as per-file options and ytdl_hook sets them file-local too, so a plain `loadfile <url> replace` loses them, and a CDN that checks Referer/Origin/User-Agent refuses the stream. It is opened with the FastStream tags, so Auto upscale and resume still know it. loadfile takes its options after its index (mpv 0.38+), and a refused loadfile only says so in its return value (validation item 3).
- A site URL opens in the default browser through ShellExecute (`rundll32 url.dll,FileProtocolHandler`; macOS `open`, else `xdg-open`), never through cmd: `cmd /c start "" <url>` would run whatever follows an unquoted `&` in the address as a command (mpv quotes an argument only when it holds a space or a quote), and the site page address comes from the website. Only a plain http(s) address without whitespace, control characters, quotes, `< > ^ { | }`, backticks or backslashes is opened; a browser percent-encodes those. Explorer is asked to select a local file (`explorer /select,`), like uosc's "Show in directory".
- The menu uses uosc's callback mode: every menu event arrives at `menu-callback` instead of uosc running item values as mpv commands.
- A FastStream stream that does not open (a refused or expired link: 403, 404, a token the site replaced) would leave an empty window with nothing said; a banner says what happened and what helps.
- `source_info-launch=no` records what would be launched in `user-data/source-info/launched` instead (the regression test); `links-for <path>` publishes the links the menu would offer for a path without loading it.

## notify.lua

- Every script sends its messages here, and this is the only script that draws them: one stack top right, below uosc's top bar and window buttons, in one design (solid black box, white title, grey detail line, a thin progress line when there is progress). Plain `mp.osd_message` would not do: mpv draws it as white text top left, where uosc's title bar covers it.
- mpv's own OSD text (menu actions like Contrast +, screenshots, `show-text` from vendored scripts) cannot be drawn here, as no script sees it. mpv.conf gives it the same look instead (`osd-box`: the same dark box, top right, the title's size), and the script keeps it right under the right-hand stack (`osd-margin-y-offset`), so the two never overlap. Its scaled pixels follow the window height, not uosc's interface scale, so the script sets `osd-scale-by-window=no` (every such option is then in real pixels) and writes the banners' own sizes into them whenever the scale or the window changes.
- Messages: `script-message-to notify show <id> <title> [detail] [seconds] [progress] [side] [icon]` and `hide <id>`.
  - `id`: a banner with the same id is replaced where it stands (five speed key presses show one banner).
  - `detail`: the grey second line, '' for none; too wide, it wraps onto up to `MAX_DETAIL_LINES` lines, so a long banner keeps the part that says what to do.
  - `seconds`: '' = `DEFAULT_SECONDS`, 0 = until replaced or hidden.
  - `progress`: 0..1 draws the progress line; the banner then has a fixed width, so a changing percentage does not make it jump.
  - `side`: "left" draws it top left (the speed banner, away from the video info); the two sides stack separately.
  - `icon`: a Material icon name from uosc's icon font (`fonts/uosc_icons.otf`, the name is a ligature); '' = the icon `ICONS` gives the id, '-' = none.
- The card: rounded like uosc's menus and buttons (uosc.conf's `border_radius`), a hairline edge so a black banner keeps its shape over a black letterbox, and on the left the same icon as the toolbar button the message belongs to, in the one accent colour of the setup (`ACCENT`, Windows 11's dark-mode accent: also the progress line and the sync tool's dragged row). Fonts are mpv.conf's `osd-font` (Segoe UI), like uosc. Text is measured with libass itself (a hidden overlay that only returns its bounds), when a banner's text changes, never per frame. ASS text is escaped so a file name can never start an override tag, and each event starts with `\rDefault`, as uosc does: mpv.conf's osd-box style would otherwise draw a second box.
- Size: every constant is a 720-line design unit times the interface scale (uosc's `state.scale`, published as `user-data/uosc/ui-scale` by a local uosc change) and `size`, a script-opt (default 1.35, `script-opts/notify_size.conf`; 1 is the original design). It applies to fonts, card metrics and mpv's own OSD text alike.
- A window narrower than a card keeps the card inside it, the detail wrapped narrower and a long title cut, so its left part (and the banner single-instance.lua's click goes to) stays on screen.
- State: `user-data/notify` = {cards = {{id, title, detail, progress, left, box}, ...}} in the order shown (a re-shown id keeps its place), and `size`. `box` (x, y, w, h in OSD pixels) is there only once the banner has been drawn (published after `canvas:update()`); with no OSD surface (`--vo=null`) no card has one.

## bottom-bar.lua

- What moves with uosc's bottom bar: the dark scrim the controls sit on, and the subtitles, which rise above the bar while it shows. Both follow `user-data/uosc/bottom-ui`, the bar's visibility and edges, which uosc publishes (a local change, AGENTS.md); music-info.lua reads it too.
- The scrim: uosc draws each control as its own black square (`opacity controls=1`), which over a picture reads as separate tiles. Instead one dark gradient is drawn behind the whole row, from clear above the buttons to black where uosc's solid-black timeline starts, and the per-control squares are off (`opacity controls=0`); uosc's icon outline (`text_border`) and hover highlight keep each control readable. The scrim fades exactly with uosc's bar, under music-info's panel and uosc.
- The lift: uosc's controls are drawn over the subtitles and cover the line being spoken. While the bar shows, and while the sync tool's panel (which sits in the same place) is open, the subtitles move up to just above it in one step: up as soon as the bar starts to fade in, down once it has faded out. Never a new value per fade step: every changed `sub-*` or `osd-*` option makes mpv reconfigure libass (sd_ass.c `SD_CTRL_UPDATE_OPTS` -> `configure_ass()` -> `ass_set_selective_style_override()` -> `ass_reconfigure()`), which empties libass's glyph, bitmap and composite caches, so every subtitle renders anew on the video thread (AGENTS.md, Troubleshooting).
- Text subtitles (SRT, WebVTT, everything mpv styles itself) move through `sub-margin-y-offset`, the option mpv provides for runtime margin changes (its own OSC uses it), an integer option: a fractional value is rejected, not rounded. Their margin is in 720-line units, scaled with the window unless `sub-scale-by-window=no`.
- ASS and picture subtitles (their own margins, which that option does not touch) move through `sub-pos`, from where the user's `sub-pos` puts them; each point away from 100 moves the line 1 % (of the video for ASS and pictures, whose libass frame is the video with `ass-use-margins=no`; of the window for text). libass moves only bottom-aligned dialogue with it: signs and `\pos` lines stay. mpv.conf removes `sub-pos` from the watch-later options, so a lifted position is never saved. A `sub-pos` change the script did not make is taken as the user's own position, read before every write, since observer notifications arrive late.
- State: `user-data/bottom-bar` = {visibility, scrim, lift_px, mode ('margin' | 'pos' | nil), sub_pos (the user's own)}.

## video-info.lua

- A small banner top right when a video starts: what it is and how big it is. It uses notify.lua's banners like every other message and disappears after `NOTE_SECONDS`.
- Title: the resolution as the picture is shown (`dwidth`/`dheight`: aspect-corrected, rotation applied, which `video-params/w`/`h` would not be). Detail, only what is known: the codec (h264 -> H.264), the pixel depth as the compiling banner words it (from `hw-pixelformat` when hardware decoding is zero-copy, `pixelformat` otherwise, which alone would say "vulkan"), and the source ("FastStream" for a whole `fs-content=` fragment item, "stream" for any other URL, "local file").
- It fires on `video-params`, which arrives with the first decoded frame: at file-loaded the decoder has not spoken yet, and a banner there would miss on streams or show the container's guess. The property fires again when a stream changes its parameters, which re-shows the banner with the new size, replaced in place. The same file and picture get no second banner.
- Songs get no banner: their "video" is cover art.

## music-info.lua

- The window title (native title bar, taskbar, and uosc's top bar in fullscreen, which inherits it) is "Artist – Title (feat. X)" for audio files, and for videos with an artist tag (music videos); a film's file name stays. With no artist found anywhere the title stays mpv's. The `title` option expands `${...}`, so a literal `$` is written `$$`.
- The cover art stays full window. For audio files a black panel with every detail the file gives (title, artist, featured artists, album, year, track, disc, genre, composer, label, audio format, what plays next) sits above uosc's bottom bar and shows and fades with it (`user-data/uosc/bottom-ui`). It reaches down to the timeline, so uosc's buttons sit on it as one black block; without cover art the window is black anyway and the panel stays.

A title tag but no artist tag: the artist from the file name when its title part matches. Featured artists ("feat.", "ft.", "featuring" in the artist or the title, bracketed or not; a marker needs a space or bracket before it and a space after it) move to their own line. ## subtitle-sync.lua

- Subtitle and audio sync on a zoomed timeline (key t, the uosc sync button `button:subtitle_sync`, or the Subtitles / Audio menus). A port of FastStream's resync tool (`chrome/player/ui/subtitles/SubtitleSyncer.mjs` and `FineTimeControls.mjs`): a strip of the timeline around the playhead, 30 s wide by default (the wheel on the time row zooms 5-180 s), with a time row, an audio row (the sound's loudness over time, so speech shows as blobs) and a subtitle row (every line as a block from its start to its end; overlapping lines go on a second lane), so the blocks can be lined up with the speech by eye.
- Mouse, inside the panel only (outside it mpv and uosc work as usual): drag the subtitle row to shift the subtitles (`sub-delay`), the audio row to shift the sound (`audio-delay`), the time row to scrub (paused while dragging, unpaused again even when the panel closes first); a click jumps there, on a subtitle block to its start; the wheel moves the row under the pointer by 0.05 s. Keys while open: Left/Right subtitles, Shift+Left/Right audio, Enter (or t) keeps both, Esc puts both back to what they were when it opened. Both delays are clamped to 300 s.
- Audio: a second mpv (mpv.exe itself, `--no-config`, no window, no sound) decodes 30 s of the selected audio track around the view and prints its loudness every 20 ms (lavfi astats -> ametadata), one run at a time, the missing chunk nearest the view's middle first. It uses the same demuxer and timeline as the player, so a beep at 3.00 s is drawn at 3.00 s, also for mkv/mp4 whose audio starts later than the video and MPEG-TS with a non-zero start. Speech band only (200 Hz - 4 kHz), and on 5.1 the centre channel, where films put the dialogue (a layout without one is downmixed). A stream is fetched again for it, with the player's headers. The drawn range is the 10th to 99.5th percentile of what is measured (digital silence left out), at least 24 dB, so a quiet mix and a loud film both fill the row and beeps in digital silence still show. The columns sit on a fixed grid of the audio's own time, so the shape stays put while the view scrolls. A read that failed (a stream's hiccup) is tried again the next time the tool opens.
- Subtitles: mpv's `sub-lines` (the lines in memory, times without sub-delay). For an external file (also a URL) that is every line, parsed by mpv itself. For a track inside the video it is only what has been read so far (a seek drops the rest), so an embedded text track is extracted in full with ffmpeg (next to mpv.exe or on PATH; not shipped), and that read is stopped when the tool closes or the file ends. Without ffmpeg (the row says where to put one), and for tracks inside a stream, the row collects the lines as playback reads them; picture subtitles (PGS/DVD) have no text list, so their lines appear as they are shown (`sub-start`/`sub-end`). ASS drawings (typesetting shapes) are no lines.
- FastStream's extras that are not ported: its voice-activity model (an ONNX network in the browser; the speech band stands in for it) and its per-line editor.
- The panel sits right above uosc's controls (their layout position, shown or not, so it never jumps when uosc fades), clear of uosc's volume slider, which is drawn over it and takes the clicks there. It sizes with uosc's interface scale, rounded and edged like notify.lua's banners, over music-info's panel and under uosc's menus. A fast mouse sends hundreds of moves a second, so a drag is drawn by the next tick.
- State: `user-data/subtitle-sync`.

## subtitle-toggle.lua

- The `c` key: no subtitles loaded -> "No subtitles", then the video's folder is scanned for a subtitle file whose name contains the video's name (exact `<name>.<ext>` first, then fuzzy, as sub-auto) and that is loaded and selected; subtitles loaded but none selected -> the first is selected and shown; hidden -> shown; shown -> hidden. With uosc, its file picker stays reachable from the right-click menu after a failed scan.
- "Has subtitles" and "has one selected" are different questions: `--subs-fallback` defaults to `default`, so when no track matches mpv.conf's `slang` and none is flagged default (a Japanese- or Spanish-only release), mpv selects no subtitle track at all.
- `sub-add`'s own result decides the banner: a file mpv cannot open or parse is not announced as loaded. `sub-visibility` persists across files, so it is set too, or a new track would load invisible after `c` hid an earlier file's.
- The binding has no key of its own: input.conf's `script-binding` line names it, as for gpu-toggles and speed-button.

## title-bar.lua

- mpv.conf's `border=yes` gives mpv the native title bar (for Windows 11 snapping), and mpv colours it by the Windows dark/light setting. mpv has no option for that colour on Windows (`--macos-title-bar-color` is macOS only), but Windows 11 (build 22000+) takes a caption, border and caption-text colour per window through `DwmSetWindowAttribute`. mpv's Lua is LuaJIT, so its FFI calls that in-process: no helper process, and the bar is black from the moment the window exists.
- On Windows 10 the call fails (E_INVALIDARG) and the bar keeps mpv's colours; that is logged, nothing else.
- Dark mode is set too, so the window buttons' glyphs are light on the black bar even with Windows in light mode. If the Windows theme switches while mpv runs, mpv re-applies the theme's value, which the script does not follow.
- The colour is set again on the properties that can bring the frame back after fullscreen; that takes a few microseconds and mpv redraws nothing.
- State: `user-data/title-bar` = {applied, hresult}.

## subtitle-cleanup.lua

- uosc's "Download subtitles" saves a stream's subtitles in `~~/subtitles` (uosc.conf's `subtitles_directory`, which a static check keeps the same as the script's); a local file's go next to it and stay. mpv never loads the stream ones again: for a URL it looks only in `~~/sub` (`--sub-file-paths`).
- So each start deletes the subtitle files there older than `days` (a week). Only files with an extension mpv takes for subtitles (`sub-auto-exts`, any case) go; other files and folders stay. A file that cannot be deleted (another mpv still reading it) stays for the next start.
- State: `user-data/subtitle-cleanup` = {sweeps, deleted, kept, failed}.

## single-instance.lua

- mpv-single.exe (what Explorer starts for mpv's file types) hands a local file to the mpv window used last that plays a local file or nothing: `script-message-to single_instance open <replace|append> <launcher> <file>...`. The script makes the playlist change itself, so it still knows what played.
- When a replace stops a file before its end, a banner top right offers "Play this in a new window" for `banner_seconds`. A click puts the old playlist back (the same file at the same second, paused if it was; auto-start.lua is told to keep that pause) and starts the launcher with `--new-window` for the new file(s), which go on in a second window where they got to. Left alone, the banner goes and nothing else happens. `append` (the rest of a burst of files opened together) only adds to the playlist, and to what a click would move.
- The banner is notify.lua's card, and its box (`user-data/notify`) the click target. The script's mouse section is on only while the pointer is over that box, and raised on every move there: uosc pushes its own click section on top whenever the pointer crosses one of its zones. Anywhere else a click stays input.conf's (pause). After the click the section stays a moment, so the second press of a double click does not reach input.conf.
- Paths compare with `/` and `\` alike and without case (Windows).
- State: `user-data/single-instance` = {offer = {old, files} while the banner offers the way back, spawned = the launcher's arguments of the last click}.

## Script modules

### faststream-fragment.lua

- How every script reads the FastStream helper's tags (AGENTS.md, "FastStream contract"): items of the URL fragment (everything after the first `#`, split on `&`), each a whole `fs-<name>=<value>` item, the last one of a name counting. A site's own query (`?x=fs-content=anime`) or an item that only ends in a tag (`#xfs-id=...`) is no tag. Plain string compares throughout, so a `%` in an address never starts a Lua pattern class. The static tier checks that no script parses the fragment itself.
- A stream mpv cannot open from its address (FastStream's helper 27: an HLS playlist at an address with no `.m3u8` and no HLS type, or one whose every file needs the address's key) plays from playlist files the helper wrote, `<temp>/faststream-mpv-hls-*/master.m3u8` or `<n>.m3u8`. Its path has no fragment, so for such a path the tags are read from `target.txt` beside it: the stream as sent, tags included, one http(s) line of at most 600 KB. Known by the folder's name alone, as Node's mkdtemp makes it (`faststream-mpv-hls-` and 6 letters or digits, `p-` before them for a private window's): the helper's temp folder and the one mpv sees need not be spelled alike (8.3 short names, `%SystemRoot%\temp` when TEMP and TMP are unset, an mpv started through WMI), so a check against TEMP missed real packages. A lookalike folder only gives tags to a file the user opened from it. Read as each file starts, by every script with the module (it observes `path`), then from its cache: a private window's folder is removed 15 s on, and a script may ask later (Auto upscale picked during playback). stream-resume, Auto upscale and the source button then treat it as the stream it is.
- `reopen_options()`: what a stream opened again (a quality switch, "Open" in the source menu) takes along: the request headers and the title the helper gave it. The header fields go as one comma list with each field's own commas escaped (mpv's list syntax); a field ending in a backslash cannot be written so and is left out, as the helper leaves it out.
- Loaded with `dofile(mp.command_native({ 'expand-path', '~~/script-modules/faststream-fragment.lua' }))`.

### state-file.lua

- How the scripts replace a state file (settings.json, speed.json, stream-resume.json, upscale.json, movie-sharpness.json) and read one. Loaded with `dofile()`, not a player script: mpv runs every .lua and every folder in `scripts/`, and says "Cannot find main.*" for a folder without a main.lua.
- `write(path, text)`: the text goes to a temp file of this process's own (two mpv windows saving at once would otherwise write into each other's), is checked (write and close; on a full disk either fails), then replaces the file in one step: `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` through the LuaJIT FFI on Windows, whose `os.rename` cannot replace a file. Elsewhere, and without the FFI, rename (which replaces on POSIX), else remove then rename. A failed save never leaves the file missing or half-written.
- `read_json(path, name)`: the file's table, nil when there is none. A file that is there but no JSON table is damaged: it is moved aside as `<file>.corrupt-<time>` (kept, never overwritten) with a warning, and nil comes back, so the script starts from its defaults instead of saving them over the file without a word. When it cannot be moved, the second value is true: the script must not save over it.
